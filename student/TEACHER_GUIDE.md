# Teacher guide: FX Crossroads playtesting

This pack is adaptable to your course/grade. It includes a testing-and-improvement assignment and a separate reflection. The game is a shared design artefact, not a test of gaming skill.

## Suggested lesson sequence

- 5–10 minutes: demonstrate the notebook, a useful bug report, and the difference between a bug, preference, balance concern and performance symptom.
- 10 minutes: pairs choose a small plan with at least three areas. Assign different heroes/modes to spread coverage. A solo route should always be available.
- 20–30 minutes: test, repeat and record evidence. Swap tester/observer roles. Keep a version/device label on every report.
- 15–20 minutes: improve the report, select three changes and prioritise them.
- Separate follow-up: reflection, peer review, then re-test a later version against the proposed acceptance criteria.

## Testing modes and shared devices

Game Dev access: Elder Ram → custom question → `gameDev` → `R4ms!`. It unlocks testing features temporarily and excludes progression/profile transfers. Student notebook reports remain exportable. Refreshing/exiting restores the normal profile.

Use disposable normal profiles for save/import tests. Download and verify a student’s personal profile before clearing a shared computer. Notebook notes are stored separately: students download their report and clear notes. New/Clear player also removes the local notebook draft. Diagnostics and notes are never submitted automatically; set a classroom submission location.

Do not require intentional graphics crashes, unsafe device changes, access to another student’s profile or public sharing of identifiable reports. An observed crash can be documented with the existing diagnostic report and a safe follow-up comparison.

## Coverage suggestions

Divide a class across: onboarding/UI, melee/ranged/support/summoner controls, mobile layout, realm navigation/objectives, PvP respawn/replay, co-op connections, profile transfer, and performance on school hardware. Each student can investigate a small slice thoroughly. Do not require all modes or all heroes.

## Assessment and accommodations

Assess evidence, methods, player impact, proposed change, trade-offs and verification. Do not assess mastery level, kills, speedrun time or ability to complete difficult content. Allow diagrams, annotated screenshots, structured bullets or recorded explanations where appropriate. No reproduction is not a failure if reported accurately.

A design improvement can earn full credit without a programming implementation. Extension: students sketch a UI/ability change, define acceptance tests and later implement a small reversible change using ABILITY_CATALOG.md.

## Closing the feedback loop

Group duplicate reports. Pick one urgent defect, one usability fix and one design experiment. Give students the resulting release notes and ask them to re-run their original tests. Require evidence before declaring “fixed.” This connects observation → proposal → implementation → evaluation.
